## myRag — минималистичный локальный RAG на SQLite и Phi‑3

**myRag** — это компактный, но взрослый пример Retrieval‑Augmented Generation (RAG), который:

- **индексирует локальные `.txt` файлы** в векторное хранилище (SQLite);
- **ищет по смыслу** через косинусное сходство;
- **отвечает на вопросы** поверх найденного контекста, используя локальную LLM **Phi‑3:mini** через Ollama;
- запускается **полностью локально**, без облаков и внешних API.

### Основные фичи

- **Чистый RAG без магии**: раздельные пайплайны наполнения и инференса, всё прозрачно и читаемо.
- **SQLite как векторное хранилище**: вектора хранятся в BLOB‑поле, без faiss/chroma и прочего тяжёлого железа.
- **HuggingFace Embeddings**: `sentence-transformers/all-MiniLM-L6-v2` через `langchain-huggingface`.
- **Локальная LLM**: `phi3:mini` в Ollama, никаких внешних запросов.
- **ОС‑агностичный запуск**: имеются `*.bat` и `*.sh` скрипты для Windows / Linux / macOS.

## Стек и зависимости

- **Язык**: Python 3.10+ (рекомендуется 3.11)
- **Хранилище**: `SQLite` (`my_rag_vectors.db`)
- **LLM**: `phi3:mini` через `ollama`
- **Векторизация**:
  - `sentence-transformers/all-MiniLM-L6-v2`
  - `langchain-huggingface`
  - `langchain-text-splitters`
- **Математика и утилиты**:
  - `numpy`, `scikit-learn` (косинусное сходство, работа с векторами)
  - `colorama` — цветной CLI

Все зависимости перечислены в `requirements.txt`.  
Создание виртуального окружения и установка пакетов автоматизированы в `init.bat` / `Init.sh`.

## Установка и подготовка окружения

### 1. Предусловия

- Установлен **Python 3.10+**
- Установлен **Ollama** и доступен в `PATH`
- Достаточно места для модели **phi3:mini**

### 2. Установка зависимостей (автоматически)

#### Windows

```bash
init.bat
```

Скрипт:
- создаст виртуальное окружение `.venv` (если его нет);
- установит зависимости из `requirements.txt`;
- проверит наличие `ollama` и подтянет модель `phi3:mini`.

#### Linux / macOS

```bash
chmod +x Init.sh
./Init.sh
```

Поведение аналогично Windows‑версии: создание `venv`, установка `requirements`, подтягивание модели.

## Как запустить весь RAG‑цикл

### Шаг 1. Подготовить данные (`data/`)

Сложи все свои `.txt` файлы в папку `data/`.  
Каждый файл — это отдельный документ (истории, мануалы, лор и т.д.).

### Шаг 2. Наполнить базу векторами (Ingestion Pipeline)

#### Вариант 1 — через Python напрямую

```bash
# Windows
.\.venv\Scripts\activate
python src\fill_db.py

# Linux / macOS
source .venv/bin/activate
python src/fill_db.py
```

Скрипт:
- загрузит и почистит все тексты из `data/`;
- нарежет их на смысловые чанки;
- построит вектора для каждого чанка;
- сохранит всё в `my_rag_vectors.db` (таблица `vector_store`).

#### Вариант 2 — интеграция в свои пайплайны

`fill_db.py` — это тонкий слой над сервисами в `services/` и `repositories/`.  
Логику можно легко переиспользовать в другом проекте или оркестраторе.

### Шаг 3. Запустить RAG‑чат

#### Самый простой способ

##### Windows

```bash
run.bat
```

Скрипт:
- откроет отдельное окно с `ollama serve`;
- активирует виртуальное окружение;
- запустит `src\main.py`.

##### Linux / macOS

```bash
chmod +x run.sh
./run.sh
```

Скрипт:
- запустит `ollama serve` в фоне;
- активирует виртуальное окружение;
- выполнит `src/main.py`.

После запуска ты увидишь приглашение:

```text
=== RAG SYSTEM INITIALIZATION ===
Config: Threshold=0.45 | Top_K=2
Type your question below. Type 'exit' to quit.
```

Пиши вопросы (на любом языке), `exit` / `quit` / `выход` — завершение.

## Подробное описание пайплайнов

### 1. Пайплайн наполнения БД (Ingestion Pipeline)

Этот процесс запускается один раз (или периодически) для подготовки данных. Его цель — превратить сырой текст в математику и сложить её в компактный векторный архив.

**Схема потока:**  
`Raw Text (.txt)` → `Splitting` → `Embedding` → `Storage (SQLite)`

**Пошагово:**

1. **Загрузка данных (`load_data.py`):**  
   Система считывает все `.txt` файлы из папки `data/` и собирает их в список строк.

2. **Очистка (`clean_data.py` → `prepare_data.py`):**  
   Тексты слегка нормализуются:
   - схлопываются лишние пробелы и переводы строк;
   - удаляются не‑ASCII символы (минимальная санитария).

3. **Нарезка на чанки (`split_data.py`):**  
   Используется `RecursiveCharacterTextSplitter`:
   - размер чанка ≈ 300 символов;
   - overlap ≈ 50 символов между соседними чанками;
   - разделители: абзацы, строки, точки, пробелы.

   Это даёт **смысловые куски контекста**, где стык между чанками не теряет смысл благодаря overlap.

4. **Векторизация (`vectorize_data.py`):**  
   Каждый чанк пропускается через модель `all-MiniLM-L6-v2`:
   - модель инициализируется **один раз** и кэшируется в памяти;
   - для каждого `Document` получается вектор длиной 384 `float32`.

5. **Сохранение в БД (`save_vectors.py` + `db_worker.py`):**  
   - векторы конвертируются в байты (`np.float32.tobytes()`);
   - в таблицу `vector_store` (`id`, `text_content`, `embedding`) вставляются пары:
     - `text_content` — строка исходного чанка;
     - `embedding` — BLOB с вектором.

Итог: у нас есть компактный локальный векторный индекс в SQLite, готовый к поиску по смыслу.

---

### 2. Пайплайн поиска и ответа (RAG / Inference Pipeline)

Этот процесс срабатывает каждый раз, когда пользователь задаёт вопрос в консоли.

**Схема потока:**  
`User Query` → `Vectorization` → `Retrieval (Math)` → `Filtering` → `Prompt Engineering` → `LLM Generation`

**Пошагово:**

1. **Запрос пользователя (`main.py`):**  
   Пользователь вводит вопрос (например: «Кто капитан Туманности‑9?»).

2. **Векторизация запроса (`vectorize_data.embed_text`):**  
   Вопрос прогоняется через **ту же самую** модель `all-MiniLM-L6-v2`, что использовалась при наполнении БД.  
   На выходе — вектор в том же пространстве, что и вектора документов.

3. **Поиск по векторному пространству (`retriever.py`):**
   - для каждого вектора из БД вычисляется **косинусное сходство** с вектором запроса;
   - результаты сортируются по убыванию схожести (`get_scored_results`).

4. **Фильтрация и Top‑K (`retriever.apply_threshold` + константы в `main.py`):**
   - берётся **Top‑K** результатов (по умолчанию `TOP_K = 2`);
   - если лучший скор ниже порога `THRESHOLD = 0.45`, система решает, что релевантного контента нет и отдаёт `None`.

5. **Промпт‑инжиниринг (`llm_service.build_prompt`):**
   - **Если контекст найден:**  
     Строится промпт вида  
     «Используя следующий контекст [контекст], ответь на вопрос [вопрос]».
   - **Если контекст не найден:**  
     Строится строгий промпт, который просит модель **не выдумывать** и честно сказать, что в базе нет нужной информации.

6. **Генерация ответа (`llm_service.call_llm`):**
   - промпт отправляется в локальную модель **Phi‑3:mini** через `ollama.generate`;
   - ответ возвращается как обычный текст и печатается в консоли.

## Как кастомизировать проект

- **Порог и Top‑K**: меняются прямо в `src/main.py` (`THRESHOLD`, `TOP_K`).
- **Размер чанков и overlap**: настраиваются в `src/services/split_data.py`.
- **Модель эмбеддингов**: меняется в `src/services/vectorize_data.py` (параметр `model_name`).
- **LLM‑модель Ollama**: меняется в `src/services/llm_service.py` (`model='phi3:mini'`).

После любых изменений в эмбеддингах **обязательно** заново прогоняй `fill_db.py`, чтобы перепостроить векторный индекс.

## Быстрый TL;DR

- Хочешь просто потыкать руками:
  - запусти `init.bat` / `Init.sh`;
  - положи свои `.txt` в `data/`;
  - запусти `fill_db.py`;
  - запусти `run.bat` / `run.sh` и задавай вопросы.

Проект специально сделан **минималистичным, прозрачным и легко хакуемым**, чтобы можно было быстро наращивать сложность (метаданные, фильтры, другие LLM, веб‑интерфейс и т.д.).
